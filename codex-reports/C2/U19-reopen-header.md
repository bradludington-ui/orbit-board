# U19: say restored work is unsaved after reopening

**Decision requested.** After ↶ Put back followed by reopening before Save, should the header continue to say “Saved …”? Recommend fixing the header now so it describes the copy currently on screen, with the previous file save shown separately.

**What is established.** The pinned status reports that restored work reopens with a “Saved …” header while the board’s record says unsaved. This is a reported finding; no fresh reproduction ran for C2. Base source inspection confirms that `keptPutBack` restores the kept copy’s checkpoint, records `dirty:true`, increments `_saveGen` and marks `DIRTY`; the header uses `unsavedNow()`, currently `DIRTY || sideUnsaved()`, and otherwise prints `MS.ts` as “Saved”. This reading identifies the distinction between a prior save timestamp and the current work’s persistence; it does not prove every startup route or a complete repair.

**Options and consequences.**

1. **Keep the existing header and rely on the detailed record.** No money or stored data changes. The visible “Saved” assurance remains false for the restored copy and can lead someone to close the browser or replace a file under the wrong assumption. A note elsewhere does not correct that assurance.
2. **Use the current authoritative save state in the header; retain the old timestamp as history.** For the reported state, say “Unsaved restored work — not written to the board file.” A separate line or tooltip may say “Last file save: …” using the last confirmed file-save record. Say “kept in this browser” only when storage was actually confirmed; if browser storage refused the write, name that limitation instead. This changes presentation and state interpretation, not entered figures or the contents of saved/kept copies.
3. **Offer or perform a save automatically on reopening.** An offer still needs truthful status. An automatic write could overwrite another copy or bypass a recovery hold; it introduces a new behavior and permission contract. It is unnecessary to fix the wording.

**Recommendation and scope.** Choose option 2 as a separate status correction. Never make the record clean, discard a kept copy or write to the file merely to make the header look consistent. The dirty generation and base record must survive reopening. A queued or older save landing must not clear restored work that was not in its bytes. If saving is held, the status should explain the hold rather than invite an operation that will be refused. While a save is in progress, “Saving …” and “restored work still unsaved” can coexist; “Saved” is earned only after the applicable write succeeds and acknowledges the current generation and relevant side lists.

**Required evidence before acceptance.** Use independently named old-file, restored and replacement copies with literal sentinel values. Put back, reopen before saving, and check header, tooltip, dirty record and actual file bytes. Cover successful next Save, failed Save, storage refusal, an earlier save landing, no-restoration clean opening, and folder/file distinctions. No failure may claim that the current work is saved, and the clean control must still say “Saved” when supported. These are proposed acceptance criteria, not completed tests.

**Money and the person’s work.** The recommended wording changes no dollar or ownership. It makes the durability of the person’s entered work visible. U19’s separate loss of the displaced saved copy remains a blocker until its preservation repair is independently verified; a truthful header does not repair that loss.
