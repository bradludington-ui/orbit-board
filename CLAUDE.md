# SPMT — Sustainment Portfolio Management Tool

A single self-contained HTML application: the FY27 Consolidated Prioritization Board. One file,
~19,500 lines, 2.8 MB, no dependencies of any kind. It runs from a shared drive or a `file://` URL
on machines with no internet route.

## There are TWO builds, and they must not diverge

| File | Look | Default theme |
|---|---|---|
| `prioritization-board.html` | cards — one panel per requirement | Midnight |
| `prioritization-board-grid.html` | grid + docked inspector | Harbor |

They are the same application. Everything except presentation — lanes, Mission Critical,
per-service flooring, every export — **must stay byte-identical**, because two copies of a
19,500-line file will otherwise drift and someone will brief the wrong number.

`tools/parity.mjs` enforces that. It extracts every top-level function from both files and diffs
them by name; anything that differs has to be named in `tools/parity-allow.json` with a reason.
`npm run check` runs it. **If you change one build, change the other** — or if the difference is
genuinely presentational, allowlist it and say why.

The grid build's additions are all *appended*, never *edited in*. In particular the inspector hangs
off `render()` by wrapping it:

```js
const _renderCards = render;
render = function(){ _renderCards.apply(this, arguments); gridAfterRender(); };
```

That is on purpose. `render()` stays byte-identical in both builds, so a change to the card build's
row template copies straight across with no merge. Keep it that way — the moment you edit
`render()` in the grid build, every future change costs a hand-merge.

Moving data between the two is the existing **File → Import**, which already reads another board's
`.html` and lifts its state out. They also share their `localStorage` key, so a draft shows up in
whichever one you open.

## This file is the source of truth

It was originally generated by `build_prio_board.py`, with helpers in a `tools/` directory
(`patch_pkg.py`, `inspect_cr_template.py`, `qpe_exact_format.py`, `measure_flow_subs.py`) and a test
suite. Comments throughout the file still refer to them, and to companion artifacts that are also
missing: `tools/sharepoint_probe.html`, and a packaged `.exe` build that makes network requests in
its own process rather than as a `file://` page with `Origin: null`. **All of that was lost with the
machine it lived on.** As of September 2026 the decision is deliberate: the HTML is edited directly,
and there is no build step.

Two consequences:

- References in comments to the build script or "the suite" are historical. Do not try to run them.
- Things the build script used to inject now have to be edited by hand. See **Hand-edit points**.

## Before every commit

```
npm run check          # invariants over BOTH builds, then parity between them
node tools/check.mjs
```

It holds the invariants the lost suite held: the script parses, the six appropriation tables agree,
the save path can still find its target, no board data is committed, and nothing external is
referenced. It exits non-zero on failure.


## The funding model — get this right before touching any export

**There are exactly two funding lanes: discretionary and mandatory.** `tiers()` is the only
authority on how a requirement's money splits. Walking the priority order, each service draws its
own discretionary lane until it is dry, then spills into that service's mandatory lane, then into
unfunded. It returns per-requirement per-service arrays `d`, `m`, `u`. Everything printed anywhere
must be derived from those, never recomputed.

The identity that must hold on every row of every tab:

```
d + m + u  ==  the requirement      (per service, and in total)
```

**Mission Critical is NOT a third lane.** It is a designation meaning "this has to be funded next
year". Its figure is the starred requirement's **own value**, and it is a **memo**: reported beside
the lanes, never added into them, and never counted toward a requirement total. It used to be
`spill` (mandatory + unfunded), which was a re-cut of dollars the Mand and Unfunded columns had
already counted — adding across the columns double-counted every starred requirement. If you find
yourself summing a Disc, a Mand and an MC column together, the model has been misunderstood.

**Mission Critical is measured against the DISCRETIONARY lane alone.** Discretionary is the money
that is actually coming; mandatory does not cover a must-fund commitment and is never netted off
it. So:

```
MC Total     =  sum of MC-designated requirement/ask values
MC shortage  =  requirement/ask value  -  discretionary allocated     (mandatory ignored)
```

`mcCalc()` is the single implementation of both rules. The board's own cutline banner, the Excel
workbook and the PowerPoint deck all read it, so they cannot disagree about what a must-pay
requirement costs. Do not recompute the star anywhere else.

These two are the stated rules and are asserted verbatim in the audit under the `RULE` label.
Change them only on an explicit instruction, and update those checks in the same commit.

### Reading a workbook, and moving one between years

**Every offset `xlsxRead()` follows comes out of the file it is reading.** A CCaR pull that did not
finish downloading points them anywhere; unchecked, a DataView read past the end threw *"Offset is
outside the bounds of the DataView"* — true, and no help to someone deciding whether to download it
again. Each read is now bounded and each failure names the fault: an empty file, no ZIP
end-of-directory record, a directory starting past the end, an entry count that runs out of file, a
zip that is not a workbook, a part missing from the zip, a failed decompression, a cell pointing
past the shared-string table (which used to yield `undefined` and land as a **blank cell** — missing
data rather than a damaged file). All four callers already surface `e.message`.

The fixture is built by the board's OWN writer, so a workbook that round-trips proves reader and
writer agree — and damaging that buffer gives realistically corrupt files instead of invented ones.

**`yearCopy()`'s own comment warned that its normalise list and its `cp()` payload must stay in step
"IN BOTH DIRECTIONS"** — a container normalised with no `cp()` arrives EMPTY and the data stays
behind, looking exactly like a year nobody filled in. That warning had no test. The oracle now reads
the container list **out of the board's source** rather than restating it, so a container added to
one side and forgotten in the other fails the day it is added. One named exception: `upl` is keyed
`'r|<id>'`, not the bare id, and is checked separately.

Also covered: award and increment dates shift with the year (a copy two years out must not still say
2026), CR half-month keys shift, the requirement value travels, a COPY leaves the source year
untouched, and a MOVE clears the order and every PMO ordering — anything less funds the same
requirement in two years at once.

### Save → reopen is an invariant, and it is tested

The board persists by rewriting its own HTML: `buildSavedHtml()` drops the whole store into the
`pubState` script tag of `SRC0`, and reopening that file is the ONLY way a save is ever read back.
If a value does not survive the trip it is gone silently, and the only evidence is a board that
looks slightly different from the one that was saved. `audit-import.mjs` boots the saved HTML in a
second jsdom — the real path, not a simulation of it — and compares.

**Three exclusions from the whole-store comparison, each deliberate:**

- `ts`, `log[].ts`, `jrnl[].t` — save clocks are MEANT to move; `buildSavedHtml()` calls `save()`.
  Zeroed **by name**, never by walking for every key called `t`: elsewhere in the store `t` is a
  title (`rcn`) and a match string (`flow.ents`).
- `pmoOrder` — rebuilt from the requirement list on load, so it is derived rather than saved.

A whole-store comparison passes the moment both sides are equally wrong, so the suite also checks
named fields one at a time: exact dollars on a trimmed allocation, a hand-typed split value **and
that it is still a number rather than a string**, the minimum useful increment, an increment's day
and its per-service dollars, a title with quotes and an em dash, a note containing `</script>`.

**The `<` escape is load-bearing, not decoration.** `.replace(/</g,'\u003c')` is what stops a note
containing a literal `</script>` from closing the tag early and truncating the entire store — the
board would not lose a note, it would not load at all. `save-no-lt-escape` proves it.

**A fixture that could not happen tests nothing.** The first run of this suite failed with a
requirement missing from `order` on reopen. That was the fixture, not the product: `BASE_ITEMS` is
captured at boot and `seed()` runs after boot, so `dataPackOf()` wrote `items:[]`. A real board has
its requirements in `DATA` at boot. The fixture now fills `BASE_ITEMS` explicitly and says why.

### Imported state is POSITIONAL, and position is not a service

Every per-service figure on the board is an array indexed by `SVC` position. A state file from a
board whose service list differs — reordered, shorter, longer, or a different set — lands each of
those arrays against the **wrong service**, and because the same dollars are all still present,
**every total reconciles and nothing looks wrong**. This was live until v1.44: the file had always
carried its own list in `dataPack.services`; nothing ever read it back.

`applyStore()` is the single choke point — the file import, the shared folder, the live view, a
board pulled from another appropriation all funnel through it. The guard sits there rather than on
each of its twelve callers, where the one that got missed would be the one that mattered. It
returns **false** on refusal and leaves the store byte-identical.

| `svcCheckPack()` says | What happens |
|---|---|
| `match` | silent |
| `reorder` | remapped **by name** after a confirm showing both lists |
| `mismatch` | refused, naming what is missing and what is extra |
| `arity` | no list in the file, but the vectors are the wrong WIDTH — refused |
| `unknown` | nothing to compare and nothing suspicious — allowed |

**A partial remap is worse than no guard**, because the rest of the board moves around the vector
left behind. `audit-import.mjs` fills every per-service vector with the file's own indices and then
walks the remapped state **generically**, failing on any service-width array that did not permute —
it does not share `svcRemapState()`'s list of what to fix, so a forgotten vector cannot pass. It
earned that immediately: `awards[].inc[].sv` carries per-service dollars and is not in
`applyState()`'s refit list either.

**Where the service list hides.** A teammate sends a STATE, not a store; `normalizeStore()` nests it
under `years.<fy>` and takes its `dataPack` down with it. Reading only `raw.dataPack` found nothing
and waved the commonest shape there is straight through. `packOfStore()` looks at the top, the
current year, and every year.

**A limit, stated rather than papered over.** `importState()`'s populated-board branch cannot be
reached from the harness: `IS_SHELL` is a boot-time const off the shipped `DATA`, and the committed
program carries none — the same rule that forbids committing a populated board. So the callers'
`if(applyStore(...)===false) return;` lines are reviewed, not covered; what they protect is a
misleading status line, and the money is covered. The mutation that targeted that unreachable line
was REMOVED rather than left as a permanent survivor or given a test that only tested itself.

### The PMO copy, and what comes back — a no-fail round trip

The board goes out to programme offices as a **sandbox copy** and their input comes back as a
submittal package. Neither leg may lose or misplace a figure, because nobody is diffing the two
files by hand and a wrong requirement value reconciles perfectly against itself.

**Outbound.** `publishPmoCopy()` writes the same self-contained HTML the board always writes, with
one extra script tag — `pubMode` → the `SANDBOX` const. Sandbox gates the **outbound** writes
(publish, shared folder, live view) and deliberately leaves `persist()` alone, so a programme office
can close the tab and come back to its own work. Nothing about the money is stripped: the copy holds
the whole portfolio and recomputes it from the same `tiers()`, so the lane vectors, the cumulative,
the tier, `natM`/`natU`, the totals and the Mission Critical memo are identical to the board it came
from. `audit-import.mjs`'s `handoff — out` block asserts that identity rather than assuming it.

**Inbound.** `pmoSubmit()` builds a package of only the contributable fields — narrative, impact,
requirement value, CCaR / PID / record name. The minimum useful increment is deliberately NOT
contributable: it is a funding decision, not a programme fact. The package carries three things
besides the edits, and each one was added because it was missing:

- `svc` — the sandbox's service list. Without it a submittal is exactly the positional-import
  hazard above, arriving through a door the guard did not watch. `pmoTake()` now checks and remaps
  by name, and refuses a different service set with the board untouched and nothing held for review.
- `base` — the values the office started from, travelling **with** the package. Recording the
  baseline at import instead meant the conflict flag could never fire: by then the board's own value
  had already been read as the baseline.
- an editor name, so a review row says who wrote it.

**Nothing is applied until it is ticked.** `pmoRows()` builds the review table, `pmoReport()` writes
it as a workbook before anything lands, and `pmoApply()` writes only the ticked rows.

**A rename that misses a call site does not throw at load.** `subBody()` emitted
`onchange="pmoPick(...)"` long after `pmoPick` became `subPick` in a collision rename. The markup was
there, the checkbox drew, clicking it raised a `ReferenceError` into a console nobody reads, and
**nothing happened** — so the only working control in the review was *Tick all*, and "nothing is
applied until you tick it" meant accept everything or accept nothing. Two things now stop it coming
back: `check.mjs` resolves **every** inline handler name in the file statically (264 of them), so it
covers panels no audit happens to open; and the import suite drives the **rendered** checkbox with a
real `change` event rather than calling `subPick()`, because calling the function behind the control
is exactly what missed this.

**A requirement added in the PMO copy is not a submittal.** The package carries *fields* of
requirements the portfolio board already has; one added after the copy was published has no id
there, so it could only ever arrive as a row the reviewer can read and never tick — while the office
believed it had submitted it. `pmoSubmit()` drops those ids and names them to the person who added
them, where they are still sitting, and tells them to raise it with the portfolio team directly.
Everything else they edited still goes.

**A package with no service list is questioned, not read.** Every submittal this board publishes
carries `svc`; one without it is damaged or hand-made, and its per-service figures would land by
position with every row total still reconciling. It now says so and names the order this board would
read them in. A package proposing only prose has no positional hazard and is not questioned.

**A PMO copy gets its own browser storage, and this is the one that would have failed live.** Every
copy shared `prio27om` with the portfolio board and with every other copy, and the boot restore
takes browser storage over the file **whenever storage's clock is later** — that ordering is
deliberate and right for the portfolio board. Copies are published days before they are distributed,
so an office that had worked in any earlier copy opened the new one and saw *that* board's numbers
under this copy's banner. Nothing looked wrong: every total reconciled. They would then have
submitted the old board's text back as new input, against a baseline it never matched, and the
portfolio team would have seen it as a proposed change with a conflict flag — a value nobody ever
typed into that copy, offered for acceptance. The key is now suffixed with the copy's publish stamp,
before `DATA` reads it: a first open falls through to the snapshot baked into the file, their own
work is restored on every open after that, and no other copy and no other board can reach it.
`PMODE.ap` pins the appropriation for the same reason — it was read from the reader's own browser
before the file had any say, so a copy could open as a drill whose data it does not carry.

**Anything that leaves a PMO copy says so.** The amber banner is on *screen*; a workbook mailed on
from a copy carried none of it. An 11-sheet export taken off a November copy was indistinguishable
from one taken off the live board this morning — same filename, same title row — so a superseded
cutline could be briefed onward with this board's own name on it. That is the same failure the
banner exists to prevent, one step further out where the banner cannot reach.

The mark rides the board's **own** convention rather than a second one beside it: `scenTitle()` /
`scenFile()` already marked a what-if view as "not the funded plan", and a snapshot is the same kind
of claim — both can be true at once. Two choke points carry it, not twelve: `expName()` for all 24
places a file gets its name, `expTitle()` for all 12 title rows. With a dozen export paths, marking
each by hand is how one gets missed. The caveat goes in **front** — callers append their own sheet
name after the title, so a mark tacked on the end lands mid-line and reads like part of that name.
A file that already says what it is (a submittal, the copy itself) is not marked twice.

Two sheets titled themselves off the raw `document.title`, which made them the only two the FY
substitution had never reached *and* the only two no mark could reach. They go through the helper now.

**The patch that added this ate its own helper.** `expTitle()`'s body contains the very expression
the rewrite was replacing, so inserting the helper first turned it into `const t=expTitle();` — a
function calling itself forever. `check.mjs` passed that file happily; only booting it caught it.
Any transform over this file must insert what it defines *after* it rewrites what it matches.

**The side databases ride alongside the store, not inside it.** Execution data (`EXDB`), the ACE cost
estimate (`ACEDB`) and the reprogramming log (`RPDB`) are their own globals, packed separately by
`buildSavedHtml()`. The handoff fixture left all three empty, so a copy that dropped one was
byte-indistinguishable from one that carried it — and a copy arriving with an empty reprogramming
tracker reads as *a programme with nothing in it*, not as a broken file. The fixture now seeds all
three with something recognisable and the copy is compared on each.

**What is reviewed must be what would land.** The review table, the spreadsheet and `pmoApply()`
all read the same package, but only `pmoApply()` put a requirement value through the board's rule
for one. A package is a JSON file, so a hand edit or a damaged transfer is all it takes: one
carrying `-5000000` and `'abc'` was *reported* as **USAF $-5,000,000 · AFRC $NaN** and *applied* as
zeroes — a spreadsheet signed off that did not describe the board it produced. `askVecOf()` is now
the single statement of that rule (`applyAskVec()` calls it too) and `pmoTake()` normalises at the
door, so every reader downstream agrees by construction. A vector of the wrong **width** is refused
rather than tidied: padding it would zero a service in silence, which is the positional hazard again
wearing a different hat.

**The change report is read back with the board's own workbook reader.** It was covered by a byte
count, which proves it downloaded and nothing else — the "a check that cannot fail reads as a pass"
trap this file keeps warning about, on the one artefact the team signs off from. Every cell is now
compared against the review it claims to describe: one row per proposed change in the review's own
order, the field, both values, the conflict column, the status column (ticked / not applied /
requirement missing), that exporting applies nothing, and that a 2,700-character impact statement
reaches the spreadsheet whole — the on-screen table clips at 300 to stay readable, the spreadsheet
is the copy of record and must not.

**`applyState()` does not own the requirement value.** A custom requirement keeps its value in
`S.custom[].ask`; a seeded one keeps it in `S.asks[id]`. `pmoApply()` wrote `S.asks` for both, so an
accepted value on a custom requirement was **silently dropped** — the review said applied, the board
showed the old number. `applyAskVec()` is now the one writer: it puts the vector where that
requirement actually keeps it, clears the stale `S.asks` entry on a custom, and `setAsk()` routes
through it too, so typing a value by hand and accepting one from a PMO cannot diverge. The
`handoff — back` block proves applying equals typing, through the real code path and across a
save/reopen.

### Appropriation packages were the other unguarded door

`applyStore()` is the single choke point where the service-alignment guard runs — and `pkgApply()`
calls it **only for the appropriation you are currently viewing**. On a consolidated board a package
for any other one was written straight into that appropriation's storage key and its `PUBS` slot:

```js
lsSet(_SLUGMAP[ap].key, JSON.stringify(next), …)   // another appropriation's storage
PUBS[ap] = next;                                    // and its in-memory slot
if (ap === mySlug()) { applyStore(next); }          // ← the guard only ran HERE
```

Unguarded, a package built for ARMY / USMC / USCG was accepted **silently** — no alert at all — and
overwrote that appropriation's figures while its stored `dataPack` still said USAF / ANG / AFRC.
Nothing covered `pkgApply` at all.

**It is checked against the services that appropriation already holds, not the ones on screen.** Two
appropriations may legitimately carry different lists; comparing to the wrong one refuses a good
package and waves a bad one through. `svcCheckPack()` and `svcGuardImport()` now take the target list
as an argument, defaulting to `SVC` for every ordinary file import.

Two things the fix has to get right, both caught by a surviving mutation rather than by reading:

- **The guard must run before `pkgStrip()`**, which copies the state, and before the preview — a
  refusal should not ask the reader anything first, and a remap must be reflected in the diff they
  are shown. Placed after the copy, the remap changed an object nobody wrote.
- **The remapped state's own `dataPack.services` must be rewritten to the target order**, because
  that list is what names the services when the appropriation is next opened. Left as the sender
  wrote it, a reload undoes the remap.

**A fixture where the two lists coincide proves nothing.** The first version gave the board and the
other appropriation the same three services, so checking the wrong list looked identical and
`pkg-svc-wrong-list` survived. The board on screen now carries STOVL / USMC-C / USN while the package
is for a USAF / ANG / AFRC appropriation.

### The change journal is the safety net, and nothing tested it

`pmoApply()`'s confirmation says, in as many words: *"Each one is recorded in the change journal, so
it can be found and undone later."* That sentence is the recourse when a programme office's proposal
is accepted in error, and it was covered by nothing. Now: a hand edit is journalled with its path,
before and after; undo restores exactly what was there; **the reversal is itself journalled** (both
entries stand — capturing the revert as an ordinary diff once folded it into the original entry and
then dropped that entry as a no-op, erasing the very change being reverted); and an accepted PMO
change can be found by path and put back.

**A value too large to have been recorded refuses to be undone.** `JRNL_BIG` caps a journalled value
at 300 characters and stores a *size* in its place; an impact statement runs well past that. Undoing
such an entry would put back a placeholder — silent data loss on the one field the whole PMO workflow
exists to collect — so `jrnlUndoable()` rejects it and says why, and the statement stays whole.

**Drive the journal the way the board does.** `jrnlSync()` re-takes the shadow *without* writing
entries; `jrnlCapture()` is what diffs it and records. Calling sync twice records nothing at all —
which the first version of this check did, and then read somebody else's entry as its own.

### Two unfunded readings, both measured against the ASK

Unfunded is **never** measured against a trimmed allocation. Money asked for and not received is
short however the allocation was cut, so both readings run off `it.ask`:

```
Unfunded vs DISC  =  ask  -  discretionary allocated              (what one pot leaves short)
TOTAL unfunded    =  ask  -  discretionary  -  mandatory          (what both pots leave short)
```

The gap between them is exactly what the mandatory pot is carrying. `discUnfSvcOf()` is the single
implementation and `mcShortSvcOf()` delegates to it — Mission Critical's shortage is this same
reading gated to starred requirements, so the star and the portfolio cannot disagree about what a
dollar is. Both are floored **per service**.

### The row is triage; the RECORD inspector is the editor (grid build)

One rule, and it is what keeps the two surfaces from growing copies of each other:

- **ROW** — only what you do while scanning 115 rows: rank and ▲▼, ★ MC, the band, and the ⋯ menu
  for lifecycle (consequence, CCaR record-name rename, reset allocation, copy/move year, remove).
  CCaR, PID, the funding mode and the award date show there as **badges**: status you need at a
  glance, with no handler. Clicking one bubbles to the row-selection delegate, so it takes you to
  the field on the right instead of doing nothing.
- **INSPECTOR** — every edit of the selected requirement. Identity, the per-service REQ / DISC /
  MAND (UFR derived), minimum useful increment, absorber, award schedule, note, description, record.

Measured, not asserted: `npm run controls` renders both builds and reports any handler present in
one and absent from the other. It compares the card's ROW against the grid's ROW **plus INSPECTOR**,
because a control that moved is not a control that was lost — and it unwraps `rowMenuRun(id,()=>{X})`,
which is only the menu's invocation shim. Anything genuinely dropped or re-implemented must be named
in that file's `RETIRED` or `REPLACED` map with a reason, or the run fails.

**`render()` stays SHARED and byte-identical.** The row's de-duplication is a post-render pass,
`gridDedupe()`, not a fork — so parity keeps protecting the one function both builds depend on.
Divergence is confined to four small presentation functions, each allowlisted.

**A near miss worth remembering:** making the funding chip a badge on *both* surfaces left the grid
with no way to set a requirement's funding at all. `convertAllToSplit()` does the whole board, but a
single row on the legacy lane walk had no path. `npm run controls` caught it. When you demote a
control to a badge, check where its capability went — "it is duplicated" and "it exists twice
because one of them is the only one that works" look identical until you try it.

**The impact statement is a ROW chip in both builds, and it is not band-gated.** "What happens if
this is not funded" is the one thing a programme office is best placed to write and the whole PMO
submittal loop exists to collect it — yet it used to appear only where `BAND_DEF().consReq` is set,
with the ⋯ menu offering it on a critical band alone. On an ordinary band there was no way in at
all. It is now in `rowChipsHtml()`, always present, labelled by state: *Impact* once written,
*CONSEQUENCE* where the band requires one and it is missing, *Impact — not written* everywhere else.
The grid inspector's copy was removed at the same time, per the rule above.

The audit for it reads the rendered **row** (`#row-A`) in both builds, not the inspector — the card
build has none, and a check that can only run in one build is a check that quietly stopped covering
the other. It matches on the live `onclick` **attribute**, not on a regex over `innerHTML`: the
handler is written with entity quotes (`toggleCons(&quot;A&quot;)`), and asserting against whatever
the serializer chose to re-escape tests the serializer.

### Harbor is the default in both builds

An unconfigured reader gets Harbor — the only palette whose lane accents a red-green reader can tell
apart (worst pair ΔE **13.1**, against 4.1–5.2 for the others; `npm run colours`). Someone who chose
Midnight keeps it: the stored value distinguishes `null` (never chosen) from `''` (chose the dark
theme), which is why those two are kept apart. `themeGet()` is now byte-identical between the builds
and has left `parity-allow.json` — an allowlist entry for a function that agrees is a licence nobody
is using, and the next real divergence would hide behind it.

**The pre-paint bootstrap is authoritative, including when the answer is Midnight.** `SRC0` is
captured *after* it runs, so every saved board and every PMO copy bakes `<html data-theme="...">`
into its own markup. Only ever ADDING the attribute meant a baked one survived a reader choosing
Midnight: `themeGet()` answered `''` and the menu ticked Midnight while the screen went on painting
the saver's theme. Clearing it makes a saved file behave exactly like a fresh one, and repairs the
files already saved. Storage being refused is an unconfigured reader too, so the bootstrap's `catch`
paints the default rather than doing nothing — it previously left `themeGet()` and the screen
disagreeing in every private window.

### Do the totals add up? — the reconciliation suite

Every other suite here derives what it expects from the board's own helpers — `tiers()`, `mcCalc()`,
`tierTotals()`. That is the right way to test that the exports agree with the board, and it is worth
**nothing** if `tiers()` itself is wrong, because then every check agrees with the same mistake.
`audit-recon.mjs` never calls a board helper to build an expectation. It asserts arithmetic that
must hold whatever the allocation algorithm does:

```
conservation   per requirement, per service:  disc + mand + beyond + trim = ask
capacity       per service:  Σ disc ≤ disc BA   and   Σ mand ≤ mand BA
cross-foot     every printed TOTAL = the sum of the rows above it, column by column
row closes     wherever a figure is broken out per service, the parts add back to it
agreement      the same quantity is the same number in every artefact that prints it
```

**Getting the identity right was most of the value.** The first version asserted `disc + mand +
unfunded = ask` and failed on exactly the two trimmed requirements, returning their trim value. That
was the *check* being wrong: the lanes conserve against the **allocation**, and the trim — asked for,
never put to a lane — is a fourth term the workbook already prints as its own column. A conservation
law you cannot state precisely is one you are not really testing.

It runs on five board shapes (a trimmed board with odd cents, a service with **no** discretionary BA,
requirements asking on one service only, pots larger than the asks, an absorber carrying the
shortfall), reconciles 16 workbook sheets, 37 breakout rows, the PowerPoint deck at its own $0.1M
precision, and the same figures after a save/reopen and inside a PMO copy.

It is load-bearing, not decorative: break `trimSvcOf`, `beyondSvcOf`, `unfSvcOf` or `discUnfSvcOf`
and it fails with 46–170 failing checks each — breaks that `tiers()` and every export would have
**agreed about**.

**Thirteen export paths leave this board, not two.** `exportExcel` and the deck were reconciled;
the other eleven had never been opened by any check. Six more produce workbooks that carry money
(the Priority Drill, Chart of Accounts, Funds Flow, Two Spend Plans, the ATR/BTR Log, Spend Plan
Source); five correctly refuse when their input is absent, and the suite now holds them to refusing
*with a reason* rather than emitting an empty file. Every workbook is read back and put through the
same two rules: a per-service breakout adds back to the figure it breaks out, and a portfolio total
is the portfolio's total.

**Six columns on the Two Spend Plans were named for the wrong quantity.** `<SVC> allocated` held
`p.want` — what *that plan* asked for per service — while the `Allocated` column beside it held
`fsDirected()`, what the board directed to the pots. Two different quantities wearing the same word:
they disagreed by **$6.25M** on the TOTAL row, and unlike `Allocated` they changed between the A and
B tabs while the sheet's own note says `Allocated` "is the same figure on every tab". The figures
were right; the name was not. They are `<SVC> asked` now, and the row closes: per service,
asked = funded + short.

**Check an identity on EVERY row, not just the total.** The plans sheet sums its TOTAL row
independently of its detail rows, so breaking `Allocated = Disc allocated + Mand allocated` on the
detail left the total correct — the mutation survived until the check walked every row. Both halves
individually defensible is how a spreadsheet comes apart in front of a room.

Three more lessons from writing it, all of the same family — **a check that cannot run reads as a
pass**: matching only bare service names left the spend plans unexamined (the suffixed `<SVC> funded`
form never matched); stopping at the first run on a header row abandoned the second, so the sheet
whose breakout had just been found wrong reported "0 breakout blocks"; and taking the *first*
`Subtotal` on the drill's band tab read band 1's figures as the portfolio's — a smaller number that
looks entirely plausible. That tab has no grand total: its band subtotals are meant to add to the
portfolio, so adding them up is also the check that nothing is double-counted or dropped between
bands.

**Two sheets said "ALL SERVICES" and meant three.** `monSheet()` builds for a FIXED service list —
RCN/EEIC is carried by `RCN_SVCS` (USAF, ANG, AFRC), Special Interest by `CR_SVCS` (STOVL, USMC-C,
USN) — and on a six-service board each printed a roll-up headed *ALL SERVICES*. The RCN sheet
totalled $14.1M against a funded topline of $23.3M and the SI sheet held the other $9.2M under a row
with the same name. **No money was lost and both were arithmetically right**; together they partition
the portfolio exactly. But a reader cross-footing the workbook could only conclude that $9.2M had
gone missing. The roll-up now names the services it covers. For the same reason the CR sheet's last
column is `TOTAL IN WINDOW`: it is the OCT–MAR cash and deliberately excludes "No date", so a column
headed plain `TOTAL` beside it read as a row total that did not add up.

**A renamed label silently disarmed the check that read it.** Renaming that CR column — at this
suite's own request — made `headerRow(..., 'TOTAL')` stop matching, and the `if (hdr >= 0)` guard
around it reported a clean pass. Every lookup in this suite now asserts that it found what it was
looking for, and the sheets it depends on are checked for existence by name. The same rename broke
three checks in `audit.mjs`, which failed loudly — those now match the roll-up by **what it is**
(the row ending `— TOTAL BY MONTH`) rather than by a name that can change.

### A hidden overlay is still a grid item

The drawer's scrim sat between `.gridwrap` and `<aside class="inspector">` inside `.gridsplit`, and
its `display:none` was declared **only inside** the `@media (max-width:1400px)` block. Above the
breakpoint it was therefore a live element in a two-column grid: it took column two, and the RECORD
panel was pushed onto a second implicit row in **column one**, rendering underneath the rows while
the 570px column beside them stayed empty. On screen the panel had simply stopped appearing.

```
1900px  columns: 1284px 570px
   gridwrap  18–1302      ← the rows
   inspector 18–1302      ← the panel, same column, underneath
```

**Every reachability check passed the whole time** — `REQ editor: 7`, `impact: 40` — because the
editors were all present and visible. They were in the wrong *place*. `editors-reachable.mjs` now
asserts WHERE the panel is: beside the rows above the breakpoint, a fixed drawer below it, and the
scrim never showing on a docked layout. Put both halves of the bug back and it reports
`panel: BELOW the rows`.

Two rules out of it. A `position:fixed` overlay belongs **outside** the grid it covers, not between
two of its columns. And a `display:none` that exists only inside a media query leaves the element
displayed everywhere else — declare the resting state at the top level and let the query turn it on.

### Layout is a correctness property, and jsdom cannot see it

**The grid build hid its only editor on the commonest screen there is.** `.inspector{display:none}`
below 1400px, and because this build deliberately retired the row editor — the row is triage, the
panel is the editor — hiding the panel left **no editor at all**. On a 1366×768 laptop the
description, the per-service requirement value and the record fields were simply gone, with nothing
on screen to say why. Six audit suites, 130 mutations and a parity diff all passed: **jsdom has no
layout**, so not one of them could see it. A real browser at a real width found it in the first
minute. Below 1400 the panel is now a **drawer** — it slides over the grid, opens when a row is
selected, closes on Esc or the scrim, and returns focus to the row it came from. One editor at every
size, which is what stops a second one growing back in the row.

Two more of the same shape, found the same way and fixed in the same pass:

- **The document scrolled sideways at 1366.** `.scores` used `repeat(4,1fr)`, and a `1fr` track
  cannot shrink below its own content — with `white-space:nowrap` inside, the widest card set a
  352px floor. `minmax(0,1fr)`, and two columns below 1400. The grid's own `--rowcols` minimums
  added to a 1150px floor; those come down below 1150 rather than scrolling, because `.gridhead` is
  `position:sticky` against the PAGE and giving an ancestor `overflow:auto` would break the pin.
- **117 chips looked clickable and were not.** `.rchip` carried `cursor:pointer` *and* a hover
  highlight for every chip — the plain badges, and every chip whose handler the grid strips because
  the panel owns that control. The one that mattered was the panel's echo of the **impact** chip:
  the single field the whole PMO workflow exists to collect, inviting a click that went nowhere.
  Both affordances now key off `[onclick]`, so they cannot drift from the handler again.

`npm run editors` (in `verify:grid`) holds all three, in Chromium, on a board with requirements on
it, at seven widths from 1920 to 1024. An empty board has no row to select and no editor to miss, so
it would pass every time while saying nothing. It is proven against the original defect: put
`display:none` back and it fails at 1400 and below.

### `npm run audit` runs BOTH builds. It used to run one.

`audit:grid` existed and nothing called it: `audit:grid` was `BOARD=… npm run audit`, so `audit`
could not call it back without recursing. The chain is `audit:suites` now, and `audit` runs it
twice — once per build. Until that changed, seven suites covered the card build and the grid build
was covered only when somebody remembered to type `npm run audit:grid`.

This is not hypothetical. Removing the impact chip from the grid row left that build with **no way
to write the impact statement at all** — the field the whole PMO submittal workflow exists to
collect — and `npm run audit` stayed green, because the check that guards it ran against the card.
`npm run audit:grid` failed immediately. **Twelve "ALL CHECKS PASSED" lines is the healthy count.**

The check itself now follows the build rather than pinning one spot: it looks for the `toggleCons`
handler on the row **and** in the RECORD panel, and prints which one answered. A surface that moves
is then a passing check that says something different, not a silent one.

### The row carries identity, money and the band

Everything else moved to the RECORD panel. Dropped from the row: the description preview, the
impact chip, the funding badge, and the dashed `+ type` prompt on an unclassified row.

Nothing was stranded, and that was checked rather than assumed before each was removed:

| Dropped | Still reachable via |
|---|---|
| description preview | the row's `⋯` menu (card), the panel's *Open on the row* group (grid) |
| `+ type` prompt | `📋 Record` in both builds — the PRIME/OGC **badge** stays on the row when set |
| impact chip | the row chip (card); the panel's *Open on the row* group (grid) |
| funding badge | never editable on the row in the grid build; the panel's BY SERVICE table sets the split, and a requirement still on the lane walk gets its own *convert to Split* chip there |

`render()` is byte-identical across builds, so the row template can only change in BOTH. Per-build
differences live in `rowChipsHtml`, which is allowlisted in `parity-allow.json` — **and the reason
recorded there has to be rewritten when the divergence changes**, or the allowlist starts asserting
something that stopped being true.

**One mutation must match both builds.** `mutate.mjs` has no way to scope a mutation to a build, so
a find string present in only one reads as NOT APPLIED there — a check that has stopped covering
anything. The panel's impact chip is therefore written with the same entity-quoted handler the card
build's row chip uses, so `impact-band-gated` catches the regression in both.

### Removing the L/M/H tier

`TIER_OF` defaulted to `'M'`, and the only place it decided anything was `proposedOrder()`, which
sorted **band → tier → current position**. It is gone; the sort is **band → current position**.

**Measured before and after, because "inert" was an assumption worth testing.** On a board with no
tier data the proposed order is byte-for-byte what it was. On a board that HAD tier data the order
does change — the tier term really was doing something there — but only in the *preview*:
`proposedOrder()` feeds `⚖ Preview proposed 1–N order` and nothing else, so the live 1–N moves only
if somebody publishes it.

Existing `S.tier` data in a saved board is left where it is rather than purged. It is never read
again, and deleting user data to tidy up is not a trade this project makes.

**Removing a column from a sheet is four edits, not one.** The header, the column width, the
detail cell — and *every total row that pads up to it with empty cells*. The suites caught all
four misses: the Decision Bands GRAND TOTAL and Subtotal rows pad with a fixed run of `''`, and so
do `ROLL` and `SUB` on the Priority Drill. A one-cell overrun shifts every figure right of it, which
`3 cross-foot` reports as 35 failures that all look like arithmetic and are really alignment.

### Photograph every panel, because arithmetic checks cannot see a panel

Seven audit suites read the workbook and the lane engine. None of them opens a modal, so a panel
could report the wrong figure — or fail to appear at all — and every suite would still pass. Going
through all 36 panels and all 8 menus one screenshot at a time found five defects nothing else
could have:

- **Spruills reported the board's own requirements as $0.00M.** `spDefs()` took `APPNS[APPN]` for
  the board's own appropriation. `APPNS` is the consolidated payload — a `const` baked in at build
  time, empty on any board that simply carries its own requirements, and `buildSavedHtml` does not
  rewrite it. So the panel printed a DELTA of the entire budget as *surplus*: FY27 read
  `+$5,476.83M` on a board holding $1,415.21M of asks, and every per-PMO row was missing.
  `pkgPackOf()` had guarded exactly this for a while (`_hasData(APPNS[ak])`, else `DATA`); `spDefs`
  now does the same. The oracle for it is derived from the scenario, never read back from
  `spGather()` — which would have agreed with the bug, sign flip and all.
- **A recorded funding source changed what a requirement was short.** See the section below.
- **`chip()` escapes its own label, and two callers escaped first.** Every funds-flow category with
  an ampersand read `Workforce &amp; Travel` on its chip. No total was wrong, so no arithmetic
  check could notice.
- **`\u{1F553}` and `\u2696` written straight into markup.** A JS escape in an HTML attribute is
  just text: the Change Journal and SPMT-vs-CCaR headings showed the escape itself.
- **`.fr` was only ever declared inside `.addp`.** The other 33 rows using it fell back to
  `display:block`, so their `gap` did nothing, `justify-content` did nothing, and a child with
  `flex:1` did not grow. Declared once at top level; the bottom margin stays scoped to `.addp` so
  no existing spacing moved.
- **`.fctab` is `table-layout:fixed`, where `min-width` is ignored.** The destinations editor
  collapsed its two free-text columns to ~100px and cut six of the eight standard destinations off
  mid-word inside their own edit boxes. Explicit `width` percentages, not `min-width`.

`npm run panels` (in `verify:grid`) opens every `.modal-bg` in Chromium and every toolbar menu,
on both builds, and asserts three things: each one **opens**, its visible text carries **no escaped
entity and no `\uXXXX` escape**, and **no `<input>` clips its own value** (`scrollWidth >
clientWidth`). Openers are read off the live DOM; the six panels needing a context — a drilled-down
cell, a selected requirement, a pending submittal — are driven explicitly, and a panel with no
entry fails rather than being skipped. Closing resets each panel's **open flag** before re-render:
stripping the `.open` class alone leaves the flag set, `render()` puts the panel straight back, and
it then sits behind the next capture and clips it. Proven against all three original defects —
restore the double-escape, the raw `\u2696`, or break `toggleBm()`, and it fails in both builds.

**`boot.mjs` resolves `BOARD` once, at module load.** Setting `process.env.BOARD` after importing it
changes nothing — the first version of this tool did exactly that and generated *two card fixtures*,
so the grid half failed at every width for a reason that had nothing to do with the product. Boot a
build from its own bytes (`boot({html: readFileSync(...)})`) instead.

### Where a split is edited, per build

The two builds deliberately differ here, and `parity-allow.json` records it:

- **grid** — the docked RECORD inspector owns the per-service Split editor. The row expander does
  not repeat it; it shows a one-line pointer instead. Two editors for one set of numbers is one too
  many, and the inspector is the one with room for six services × four money columns.
- **card** — has no inspector, so the row expander keeps the editor as its only one.

`migrateSplit(id)` promotes a legacy whole-requirement split to per-service vectors. It used to run
inside the row expander's render; it is now a shared function called by both builds, so removing
that editor from the grid could not take the migration with it.

The inspector's split table is `table-layout:fixed` with a `<colgroup>`. Without it the columns are
content-sized, so the moment a UFR cell turns from an em dash into a dollar figure every other
column resizes — while the user is typing into them.

### Every requirement carries an explicit Split

`auto (lanes)` is gone from the funding menu, as Force DISC/MAND/UFR were before it. `tiers()`
still walks the lanes for a requirement with no override — an older saved board, or one
mid-migration — so nothing breaks on load; it simply cannot be chosen.

- `seedSplit(id, T)` freezes ONE requirement's current lane draw as directed per-service dollars.
  One implementation, shared by the chip, the bulk convert and a newly added requirement.
- `convertAllToSplit()` moves a whole board over. It is a one-way bulk edit with **no undo** (the
  board has no undo stack), so it confirms with a count and points at Snapshots.
- `addReq()` seeds a new requirement on Split, because the menu can no longer offer auto.

**Conversion is lossless, and that is the property to protect.** Every dollar and both unfunded
readings are identical before and after — `tiers()` re-reads exactly what it just produced, and
unfunded is ask-based either way. `audit-board.mjs` asserts this across two fixtures, one with a
SCALAR trim so the per-service values are fractional: `seedSplit` rounds each service to whole
dollars, and whole-number fixtures would make that rounding invisible. If conversion ever shifts a
dollar it will do so across every requirement at once and silently.

### A recorded funding source moves no money

`basisSvcOf()` used to return the full ask for a requirement carrying a directed funding source,
and the board allocation for every other. That made the same money carry two different names: the
gap between ask and allocation is TRIM on an ordinary requirement, but on one with a source
recorded against it the identical gap came out as BEYOND BOTH LANES — and beyond is what the
portfolio shortfall banner counts.

Because `seedSplit()` fills the directed dollars **from the current allocation**, the consequence
was that recording where money came from — moving no money whatsoever — flipped a requirement from
"fully funded" to "partly unfunded" and grew the banner. On a 115-requirement board that read as a
$38,325,128 portfolio shortfall which was entirely trim on the 7 requirements that happened to have
both, on a board whose lanes held $5.48B against $1.42B of asks and whose true lane shortfall was
**zero**. Two rows identical in ask, trim and funding sat side by side on the 1-N report reading
"fully funded" and "partly unfunded $4,671,122", with nothing on screen to say why.

The basis is the allocation now, for every requirement. A source says where the ALLOCATION is drawn
from; it is not a claim on the untrimmed ask. Everything else is unchanged: unfunded stays ask-based
(`beyond + trim == unfunded` still holds per service and in total), and the $107,017,782 the
workbook prints as TOTAL Unfunded did not move.

**The rule was written out three times** — `tiers()`, `basisSvcOf()` and `aOf()` in the workbook's
Unfunded Requirements sheet — so changing it in one place left the other two behind and the audit
caught the disagreement immediately. All three read `basisSvcOf()` now.

**`seedSplit()` no longer rounds.** It recorded the lane draw rounded to whole dollars, which was
invisible while the basis was the ask (the rounded figure sat well under that ceiling and passed
through untouched). Against the allocation, a value rounded DOWN loses its fraction to unfunded and
one rounded UP is capped — so converting a board to Split stopped being lossless, by cents, on
every requirement at once. `audit-board.mjs` catches it through the fractional-trim fixture, which
exists for exactly this.

Two guards hold the property: `a recorded funding source moves no money` in `audit-board.mjs` (two
copies of one requirement, differing only in whether a source is recorded, asserted equal on
discretionary, mandatory, beyond, trim, unfunded, basis and tier), and the `basis-fsrc` mutation,
inverted to put the old ask-basis back.

**EVERY per-service figure is floored PER SERVICE, not once on the totals.** A "service" is a
service AND ITS VARIANT — STOVL, USMC CV and USN are each their own pot — and money never moves
between them, so an over-allocation in one can never pay down a shortage in another. This governs
the MC shortage and unfunded alike. The two readings agree on any board with no over-allocation,
which is why only a deliberately over-allocated scenario pins it down.

`unfSvcOf()`, `beyondSvcOf()` and `trimSvcOf()` are the single implementation, defined next to
`mcCalc()`. Both exports and the Decision Bands sheet read them. Defined so that, per service and
in total, `beyond + trim == unfunded` always — including an over-allocated service, where the trim
is nothing and the lane shortfall is capped at the ask.

One consequence worth knowing: where a service is funded beyond its ask, `funded + unfunded`
exceeds the requirement. That excess is real money and does not vanish. The identity that holds is
`funded + unfunded == max(ask, funded)`, per service.

A starred requirement carried entirely by the mandatory lane is **fully short**. A starred
requirement trimmed on the board is short by the trim, even if discretionary covered the trimmed
amount in full. `tiers()` draws discretionary before it touches mandatory, so `p.d` is already the
discretionary-only answer — there is no need for a second walk (that is what `{noMand:true}` and
`scenView==='disc'` exist for elsewhere).

Exports carry two MC memo figures: **★ MC requirement** (the starred requirements' own value) and
**★ MC short vs Disc** (the gap that drives the ask). Neither is ever added into a lane total.

**"By PMO" means one thing everywhere.** `pmoSharesOf()` returns `[group, fracPerService]`; a
CLIN-backed prime is split across the offices owning its CLINs. Weight **per service**
(`x[i] * frac[i]`) — never by an average across services. Every by-PMO view in the workbook uses
this, so the tabs reconcile against each other.

`GROUPS` is the *configured* PMO list and is not the whole truth: `pmoSharesOf` can derive `PRIMES`
from a CLIN suffix, and a PMO removed from the list leaves its requirements behind. Never iterate
`GROUPS` alone to emit rows — use `pmoKeys()`, which puts the configured offices first and appends
anything else rather than losing it.

A requirement split across offices is counted in **each** row it touches, so a by-PMO count column
must total the requirements on the board, not the sum of its own rows — otherwise a prime split
three ways reads as three requirements.

One implementation each, all hoisted beside `mcCalc()` so the workbook, the deck and the board
cannot diverge: `pmoKeys()`, `mcShortSvcOf()`, `unfSvcOf()`, `beyondSvcOf()`, `trimSvcOf()`.

### The ◨/◧ view toggle — discretionary only vs discretionary + mandatory

The board can be read two ways, and the toggle switches between them **for the spend-plan family
only**. `scenView` is the state (`''` or `'disc'`); `scenOpt()` returns `{noMand:true}` under
"Discretionary only", which runs the ordinary lane walk with **every mandatory lane empty** — so
what would have spilled into mandatory shows as unfunded and never reaches a month. There is no
second engine: it is `tiers()` with one option.

**What follows the toggle** — exactly three things, and nothing else:

| Surface | How |
|---|---|
| RCN-EEIC by Month (sheet) | `const Tv = scenOn()? tiers(null, scenOpt()) : T` |
| SI Codes by Month (sheet) | the same `Tv` |
| Spend forecast **tab** (on screen) | `forecast()` bare: `const T = fundOf ? null : tiers(null, scenOpt())` |

**What must NOT follow it:** every other sheet in the workbook, the deck, and the board's own
totals. Unfunded Requirements is ask-versus-allocation rather than a lane shortfall, so the toggle
would misstate it. The audit compares **every sheet** between the two views, not just one — the
month sheets are built partway through `exportExcel`, so a view leaking into the shared `T` would
corrupt only the sheets built *after* them and a single-sheet check sails straight past it.

**The `<FY> Two-Plan Forecast` SHEET is deliberately on the invariant side.** It is not the board's
forecast: it is PLAN A (discretionary only) and PLAN B (disc + mandatory) printed side by side, both
modelled through `fundOf`. It already shows both answers at once, so the toggle must not move it.
The on-screen forecast tab is the one that follows the view. These are different objects — do not
"fix" the sheet to match the tab.

The sheet was called `<FY> Spend Forecast` until it was renamed for exactly that reason: one word
away from the tab, and readers compared a two-plan model against one set of allocations. The audit
matches it on `/Forecast/` and **fails when it is missing** rather than skipping — the old
`if (fc)` meant a rename would have quietly disabled every check on the sheet while the suite still
read green.

**The marker is part of the behaviour, not decoration.** A workbook built under "Discretionary
only" is a WHAT-IF, and stops being obviously one the moment it is emailed. `scenTitle()` stamps
the month-sheet titles, `scenFile()` appends `[DISC-ONLY]` to the file name, and `fcBody()` marks
the on-screen forecast panel. Each is asserted in **both** directions — present under the toggle,
absent without it — the two exported ones in `audit.mjs`, the on-screen one in `audit-board.mjs`,
because it is rendered and never exported and no export suite can reach it. Never ship a figure
that moves with the view without a marker saying so.

### Auditing the exports

```
npm install        # jsdom, for the audit only
npm run audit          # all four suites
npm run audit:export   # the Excel workbook (exportExcel)
npm run audit:ppt      # the PowerPoint deck (exportPPT)
npm run audit:other    # the Priority Drill (exportCSV) and Exec Synopsis (execSynopsis)
npm run audit:board    # figures the board derives and never exports
```

Point any of them at the grid build with `BOARD=$PWD/prioritization-board-grid.html`.

**Which exports do lane math at all.** Four do it directly: `exportExcel`, `exportPPT`, `exportCSV`
and `execSynopsis`. ACE Tie-Out, Chart of Accounts, ATR/BTR Log and CR Cash Return reconcile against
imported sources and never touch `tiers()`, the star or unfunded, so they stay outside these suites.

**The month-by-month sheets are the exception, and they are easy to miss.** *Spend Plan Source* is
an IMPORTED workbook, not an export — do not go looking for it here. What spreads `tiers()` output
across months is:

- `monSpreadOf` → the **RCN-EEIC by Month** and **SI Codes by Month** sheets
- `forecast()` → the on-screen spend forecast tab, and the **<FY> Two-Plan Forecast** sheet (two modelled plans)

**Those are two copies of the same spread and they must not drift.** `forecast()`'s own comment says
so, and they drifted anyway the moment one was changed alone. Change one, change the other.

They differ in exactly one respect, and it is deliberate. An increment is DOLLARS only against the
board's own allocation: `forecast()` bare and `monSpreadOf` spread what the board actually funds, so
what was typed is what lands. `forecast(fundOf)` spreads a MODELLED plan whose dollars are not the
ones the increments were sized against, so there the increments carry only the SHAPE of the
schedule. Spreading a model literally strands most of it in UNSCHEDULED.

Both carry a conservation property: every funded dollar lands in a month or in UNSCHEDULED, never
dropped and never invented. All of it is asserted in `audit-board.mjs` rather than the export
suites, because this is board logic that exports happen to consume.

**The suite's epsilon is 0.005 DOLLARS.** The Two-Plan Forecast sheet prints in $M, where that tolerance
is enormous: a whole dropped PMO came to 0.000012 and passed. Scale to dollars before comparing
anything printed in millions.

`tools/export-audit/` boots the real board in jsdom, seeds boards with deliberately uneven
per-service numbers, runs the real `exportExcel()` and `exportPPT()`, and checks every printed
figure against `tiers()`. Add a scenario there before changing export math. The board itself still
has **no** dependencies — jsdom is dev tooling and never ships in the HTML.

### Measuring the suites — run this after adding checks

```
npm run mutate            # all mutations
npm run mutate -- mc      # just the Mission Critical ones
```

Green suites prove nothing on their own: a check that never runs looks exactly like a passing one.
`mutate.mjs` breaks one line of export math at a time and requires a suite to fail. A mutation whose
search string no longer matches is reported **NOT APPLIED**, never as caught — a stale target must
not masquerade as coverage.

Every surviving mutation is a line nothing protects. Add the check, do not delete the mutation.
Four kinds of gap it has already found, none of which the checks alone would have shown:

- **Conservation is not enough.** `d + m + u == basis` still holds when a draw is merely mis-split —
  short-change the discretionary draw and the shortfall moves into mandatory, every total ties. The
  suite now re-derives the greedy walk independently (the "lane oracle") and compares draw for draw.
- **A check that cannot run reads as a pass.** Assertions matched on a title the slide never renders,
  and a figure was computed but never asserted. Both looked green for as long as they existed.
- **AN ORACLE THAT ASKS THE CODE UNDER TEST WILL AGREE WITH IT.** The lane oracle obtained the
  allocation basis by calling `svcAlloc()` in the page, so a mutation splitting a trimmed allocation
  evenly across services — instead of weighting it by each service's ask — passed every suite. The
  sheets faithfully printed the wrong split and the oracle confirmed it. `basisOf()` in `audit.mjs`
  now restates the rule from the scenario's own inputs and never reads it back from the page.
  **Derive expectations from the fixture, never from the code you are testing.**
- **A path with no fixture has no coverage, however many checks point at it.** Every scenario passed
  a per-service allocation vector (`m:'s'`), so the scalar-trim branch of `svcAlloc` — one figure
  typed into the row's allocation box, the commonest edit on the board — was never once executed.
  Likewise every funding-source override sat on a requirement with no allocation, making "basis on
  the full ask" and "basis on the allocation" indistinguishable. Both now have scenarios.
- **A figure the board shows but never exports is invisible to export suites.** The cumulative could
  be made to skip unfunded dollars entirely with all three export suites green, because no export
  carries it — and it is what places the cutline banners. Sweeping the scoreboard tiles and the
  discretionary fit strip afterwards found **every one of their figures equally unprotected**,
  including the PROGRAM FLOOR, which is one of the two stated Mission Critical rules. `audit-board.mjs`
  covers the board's own derived figures; add to it rather than stretching an export suite.
- **Read the rendered page, do not recompute.** `audit-board.mjs` pulls each tile's figure out of the
  DOM. Re-evaluating the same expression in the harness would compare a copy against a copy and pass
  whatever the board did — the lane-oracle trap in a different costume. A pattern that no longer
  matches is recorded as a FAILURE, never skipped.
- **`typeof x === 'function'` on an out-of-scope name fails OPEN, silently.** The grid inspector read
  `★ MC shortage` as `(typeof mcShortOf === 'function') ? mcShortOf(it) : 0`. `mcShortOf` is a
  `const` **inside `exportExcel()`**, so it is not in scope there — and `typeof` on an undeclared
  identifier returns `'undefined'` instead of throwing, so the guard swallowed it and the field read
  0 for every requirement. Every starred row said "covered", however short it was, for as long as
  that line existed. A guard that turns a missing dependency into a plausible default hides the
  failure it was written to reveal; call the global helper and let a genuine mistake throw.
  It survived because `inspector-agrees.mjs` compared requirement, discretionary, mandatory and
  unfunded — but never the MC field. **A rendered figure with no assertion is decoration.**
- **A scenario absent is a rule untested.** No board scenario had a starred requirement, so all four
  Mission Critical tile figures were being compared against zero and agreed. Adding MC scenarios also
  exposed a bug in the harness's own tier oracle, which had missed the line that makes a must-pay read
  `mc` only once mandatory or unfunded touches it.
- **"Nothing else moved" has to be checked on everything, not on one example.** The view toggle's
  scope check asserted that Unfunded Requirements was unaffected — and a mutation that leaked the
  view into the shared truth walk survived it, because that sheet's rows are computed *before* the
  month sheets and the leak could only corrupt what came after. The check was guarding the one sheet
  the bug could not reach. It now compares **every sheet** between the two views. When a rule says
  "and nothing else changes", enumerate the everything; a representative sample picks itself for
  the wrong reasons.
- **A string check in a numeric harness fails silently in the wrong direction.** `chk()` compared with
  `Math.abs(got - want) <= EPS`; handed two equal strings that is `NaN <= EPS`, i.e. false, so every
  marker assertion "failed" and then crashed the reporter on `got.toFixed`. The crash was the lucky
  part — had `chk` returned a pass for non-numbers instead, the marker checks would have read green
  forever. Widen the comparator with the assertion, not after it.

**Equivalent mutations.** Two are marked `equivalent:` rather than surviving: flooring the lane
remainders cannot change any output, because every draw is clamped by `Math.max(0, dRem[i])` and
nothing can drive a remainder negative. That is a claim with a receipt — `audit-board.mjs` asserts
the clamping invariants, so if a clamp is ever removed the mutation stops being equivalent and the
suite fails. Mark a mutation equivalent only with that kind of backing; a survivor that is merely
inconvenient is still a survivor.

## Never commit a populated board

The repo holds the **program**. A working board is program and data fused into one file (see
below), and that data is budget detail that does not belong on GitHub. The committed copy must
always have `pubState` as `null` and `APPNS` empty — `check.mjs` enforces both.

To work on a change against real data, describe the data shape rather than uploading the board.

## How it saves — read this before changing anything structural

The file is its own database.

- `SRC0` is captured at boot as `'<!DOCTYPE html>\n' + document.documentElement.outerHTML`.
- `buildSavedHtml()` takes `SRC0` and **regex-replaces the `pubState` script tag** with the current
  state as JSON.
- `saveInPlace()` writes that back over the file itself via the File System Access API
  (`showSaveFilePicker`), caching the handle in IndexedDB (`prio-fh`), with a timestamp collision
  guard that warns when a colleague saved after you loaded.

So: **the `pubState` tag's exact literal shape is load-bearing.** Reformat it and `Save` silently
writes a file containing the *old* state. `check.mjs` guards this.

`localStorage` is a convenience cache only — the file is the record. Keys: `prio27om`, `prio27ff`,
`prio27sp`, `prio27opn`, `prio27execdb`, `prio27acedb`, `prio27reprog`, `prio27appn`, `prio27who`,
`spmtTheme`, `spmtSidecar`.

Six tables must change together. The file's own comment at `APPN_SLUGS` explains why this is
dangerous: a slug missed in one table does not throw. It quietly covers one appropriation fewer — a
chip row missing a button, an export summing three of four — and every figure it still prints
reconciles, so nothing looks wrong. `check.mjs` is the replacement for the suite check that used to

## Colour: one token, one job

Two tokens were each doing two jobs, and both only showed up when a light theme arrived:

- `--red` was the unfunded **data** lane *and* the alarm **status**. Unfunded is now `--unf`/`--unfD`.
- `--onGold` was text on the gold accent fill *and* text on the fixed `GCOLOR` pastel PMO chips.
  Chip text is now `--onChip`, set once in `:root` and deliberately never overridden — those
  pastels are theme-independent and always light, so the text on them is dark in every theme.

If you find yourself tuning a token for one context and breaking another, that is the signal to
split it rather than compromise.

`Harbor` is the first palette built for colour-deficient reading rather than tinted for it after
the fact. Its lanes leave the green/red axis entirely — blue discretionary, ochre mandatory,
**neutral** unfunded. Unfunded is colourless because a sweep of the whole hue wheel showed no
colour beats a neutral once the third lane must stay readable as text *and* stay apart from the
other two for a red-green reader. Nothing in it is colour-alone: lanes carry their word, unfunded
is a dashed outline, Mission Critical is the star glyph.

Check colour with numbers, never by eye — **`npm run colours` now does it**, in a real browser, for
every theme and both builds. The validator is vendored at `tools/vendor/validate_palette.mjs`
because it ships with a skill in a temp directory: a check that depends on that would pass today and
vanish tomorrow.

**What actually protects a colour-deficient reader here is not the lane hues.** The charts carry
meaning by fill **density** — solid discretionary, hatched mandatory, open dashed unfunded — off a
single blue ramp (`--fcSolid` / `--fcMand` / `--fcEdge`, 7° of hue between them), so they read the
same in greyscale and under every deficiency. The lane hues (`--green`, `--purp`, `--unf`) tint
labelled cards and chips, where the word is beside the colour. So the checks are:

| Held | Why |
|---|---|
| the chart never references a lane hue, and still draws its hatch | the real guarantee, asserted against the **rendered** SVG |
| its fills stay one hue ramp | a well-meant tweak giving mandatory its own colour breaks greyscale |
| Harbor clears the CVD gate (ΔE ≥ 8) | it is the theme that promises this — it measures **13.1** |
| no theme's lane separation gets worse than baseline | records the truth without pretending |
| text clears WCAG (AAA body, AA muted and dim) | measured 12.3–15.9 : 1, 7.2–7.4 : 1, 4.9–6.1 : 1 |

**The measured truth, recorded rather than papered over.** Worst all-pairs CVD ΔE on the three lane
accents: Midnight **5.2**, Navy **4.1**, Parchment **4.8**, Blueprint **4.7**, Harbor **13.1**. The
validator's floor is 6.0. Four themes sit on the green/red axis and their discretionary and unfunded
accents are hard to tell apart for a deuteranope — which is the pre-existing design and exactly why
Harbor was built. Those numbers are a BASELINE, not a gate: a token tweak that makes any theme worse
fails loudly, without asserting a standard those four palettes were never built to meet. **The card
build still defaults to Midnight**; the grid build defaults to Harbor.

Each guard is proven against its own failure: point the chart at `var(--purp)` → *leaked: --purp*;
put Harbor's unfunded back on red → *worst ΔE 4.1 (gate 8)* and a baseline regression; dim `--mut` →
*1.6:1*.

## House style

Match what is there. The file explains *why*, not *what* — the comments record the failure that
motivated the code ("this was duplicated in nine places and the missed one does not throw"). That
is why it is maintainable by someone who did not write it. Keep it.

Errors degrade rather than throw: an unknown appropriation slug falls back to the slug itself,
because a board that covers one appropriation oddly is recoverable and a board that will not open
is not. Preserve that posture.
